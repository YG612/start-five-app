# 1. Codex 执行协议

## 1.1 任务卡字段

每项需求使用固定字段，Codex 不得自行省略：

```text
ID       唯一任务编号
P        优先级：MUST / SHOULD / LATER
USER     用户遇到的问题
GOAL     用户可感知结果
ENTRY    入口或触发条件
FLOW     用户操作流程
RULE     业务与交互规则
DATA     数据、迁移、接口要求
METRIC   可量化指标
AC       验收条件
TEST     必须增加的测试
NO       禁止实现方式
```

## 1.2 阶段执行规则

1. P0-P6 已完成，不得重做。
2. 每轮只执行一个阶段；禁止同时改 P7-P10 全部功能。
3. 先定位现有实现，再做最小增量；不得建立第二套 Repository、Runtime、计分、通知或备份系统。
4. 每个阶段先完成 MUST，再做 SHOULD；LATER 只记录，不实现。
5. 每个阶段完成后运行定点测试、TypeScript 检查和有限兼容测试。
6. 不能运行的 DEVICE / iOS 验收必须标记为 `PENDING_EXTERNAL`，不得声称通过。
7. 发现需求冲突时，优先级为：数据安全 > 核心闭环 > 无障碍 > 便捷性 > 动效装饰。
8. 不等待用户确认；在不破坏数据的前提下做最小、可回滚的实现。

# 2. 固定产品原则

## UX-01 任务先于产品概念

用户打开 App 是为了知道“现在做什么”，不是理解“工作台、运行时、回执、事务、幂等”。所有工程概念只能出现在代码、日志和开发文档中。

## UX-02 一个界面只突出一个主行动

首页主行动按以下优先级显示：

```text
活动专注 > 继续上次任务 > 现在最适合开始 > 普通地图浏览
```

同一屏不得同时出现两个同等视觉权重的主按钮。

## UX-03 渐进展开

高频操作先显示，低频字段后展开。点击任务后先看到：

```text
先做 5 分钟 / 完成 / 重新安排 / 我卡住了 / 更新进度
```

完整标题、坐标、备注、重复规则等进入“编辑更多”。

## UX-04 自动化必须解释

系统自动推荐、自动提高紧急度或生成下一次任务时，必须说明原因，并允许修改或撤销。

## UX-05 失败后修复，不羞辱

延期、低状态、救援和放弃都不得扣除既有总积分，不得使用羞辱、威胁、人格评价或医疗诊断文案。

## UX-06 所有隐藏手势都有可见替代

拖动可以作为便捷方式，但任务面板必须提供象限选择；滑动完成可以保留，但必须有可见完成按钮。

## UX-07 用户数据优先

保存失败不清空输入；提醒失败不回滚任务；积分失败不回滚任务完成；迁移失败不能导致整个任务库无法打开。

## UX-08 默认离线、默认私密

本轮不增加网络、账号或云端依赖。任务标题、备注、拖延原因不得上传。产品指标默认使用本地/测试注入，不接第三方分析 SDK。

# 4. 指标体系

## 4.1 发布门槛指标

**KPI-G01 首页可交互时间**  
目标：Android 真机 p75 ≤ 2.0s；p90 ≤ 3.0s。验证：DEVICE + 本地指标。失败：未真机只能标记待验收，不可声称通过。

**KPI-G02 点击任务到操作面板可用**  
目标：p95 ≤ 250ms。验证：AUTO + DEVICE。失败：先移除同步重计算和阻塞动画。

**KPI-G03 打开首页到开始已有任务**  
目标：中位数 ≤ 8s；p90 ≤ 15s。验证：UTEST，5 名首次用户。失败：不补教程，先减少点击与文案。

**KPI-G04 快速创建普通任务**  
目标：中位数 ≤ 10s；p90 ≤ 18s。验证：UTEST。失败：继续收敛默认字段。

**KPI-G05 操作层级**  
目标：点击任务后，开始、完成、重新安排最多再点 1 次。验证：AUTO + UTEST。失败：不允许跳完整详情页。

**KPI-G06 保存反馈**  
目标：UI 乐观更新 ≤ 100ms；本地持久化 p95 ≤ 500ms。验证：AUTO + DEVICE。失败：保留输入并显示重试。

**KPI-G07 完成到成长反馈**  
目标：≤ 1000ms。验证：AUTO + DEVICE。失败：动画不得阻塞数据提交。

**KPI-G08 核心流程可学会性**  
目标：5 人中 ≥4 人无需说明完成核心流程。验证：UTEST。失败：优先改层级、按钮和词，不加长教程。

**KPI-G09 坐标理解**  
目标：5 人中 ≥4 人在 10 秒内解释“右=重要、上=紧急”。验证：UTEST。失败：加强轴标签和象限副标题。

**KPI-G10 数据完整性**  
目标：自动化场景 100% 无丢失、无重复任务、无重复积分。验证：AUTO。失败：阶段阻断。

**KPI-G11 无障碍**  
目标：关键点击区 ≥44dp；关键控件 100% 有角色和标签；最大字体不裁切。验证：AUTO + DEVICE。失败：阶段阻断。

**KPI-G12 地图拖动成功**  
目标：20 次真机拖动 ≥19 次落入预期象限；每次最多一次持久化。验证：AUTO + DEVICE。失败：优先修手势冲突和吸附。

**KPI-G13 规则输入解析**  
目标：支持语料准确率 ≥95%；不支持语料 100% 可退化为纯标题。验证：AUTO。失败：解析失败不得阻止保存。

**KPI-G14 卡住到开始**  
目标：中位数 ≤ 25s；交互 ≤4 次。验证：UTEST。失败：减少问题数量，不引入复杂诊断页。

**KPI-G15 通知精确性**  
目标：冷启动、热启动、重复点击 100% 定位正确任务且不重复会话。验证：AUTO + DEVICE。失败：阶段阻断。

**KPI-G16 构建回归**  
目标：原 89 项基线测试继续通过；新增测试通过；Android internal 构建通过。验证：AUTO。失败：阶段阻断。

## 4.2 产品效果观察指标

这些指标需要先建立基线，不在首轮设虚假增长目标。代码只需提供无隐私的测量能力。

```text
OM-01 五分钟启动率
= 发生 focus_started 的独立任务数 / 被打开的独立未完成任务数

OM-02 首次启动提前量
= dueAt - firstFocusStartedAt
目标方向：逐周增加

OM-03 成长区主动启动占比
= 成长区首次启动任务数 / 全部首次启动任务数
目标方向：增加

OM-04 救火区任务占比
= 有效象限为救火区的未完成任务数 / 未完成任务数
目标方向：下降

OM-05 延期后修复率
= 延期后 24 小时内发生 repair_applied 或 focus_started 的任务数 / 延期任务数
目标方向：增加

OM-06 卡住修复后启动率
= stuck_flow_open 后 30 分钟内 focus_started 的任务数 / stuck_flow_open 的任务数
目标方向：增加

OM-07 通知行动率
= 通知动作触发的 focus_started 或 reschedule / 通知展示数
目标方向：增加
```

## 4.3 本地指标端口

新增或复用可注入端口：

```ts
export type ProductEventName =
  | 'home_ready'
  | 'task_sheet_open'
  | 'task_create_open'
  | 'task_create_saved'
  | 'task_move_committed'
  | 'task_move_undone'
  | 'focus_started'
  | 'focus_resumed'
  | 'task_completed'
  | 'task_completion_undone'
  | 'reward_shown'
  | 'stuck_flow_open'
  | 'repair_applied'
  | 'low_energy_changed'
  | 'rescue_plan_created'
  | 'notification_action';

export interface ProductMetricEvent {
  name: ProductEventName;
  occurredAt: string;
  sessionId: string;
  source?: string;
  durationMs?: number;
  success?: boolean;
  errorCode?: string;
  taskRef?: string; // 仅测试/本地调试，不记录标题和备注
}

export interface ProductMetricPort {
  record(event: ProductMetricEvent): void | Promise<void>;
}
```

规则：

1. 生产默认 `NoopProductMetricPort`，不得联网。
2. 测试使用 `InMemoryProductMetricPort` 断言事件与耗时。
3. 如提供开发调试缓冲区，最多 500 条，用户主动导出；不得包含标题、备注、拖延答案、通知正文。
4. 指标失败不得阻断用户操作。

# 5. 全局界面与行为约束

## UI-G01 首页信息密度

以 360×800dp 为最低参考屏：

1. 四象限地图无需纵向滚动即可看到四个区和至少一个任务节点。
2. 地图可视高度不低于可用内容区的 50%。
3. “继续上次任务”和“现在最适合开始”不得同时以展开大卡片出现；继续任务优先，推荐降为单行。
4. 首页持久主按钮最多一个。
5. 顶部不显示大型统计卡、备份、历史、今日收尾或多个入口矩阵。

## UI-G02 任务面板

1. 标准字体下主按钮不滚动即可见。
2. 字体放大时允许内容滚动，但主操作使用安全区内粘性底栏。
3. 标题最多两行；第一小步最多两行；完整内容进入详细层。
4. Bottom Sheet 打开后焦点进入标题/主操作；关闭后返回原任务节点。

## UI-G03 文案

用户文案必须：

```text
短句、具体、不责备、说明下一步、说明数据是否安全。
```

禁止词：

```text
运行时、幂等、工作台、回执、事务、journal、repository、状态机、同步命中、冷启动命中。
```

## UI-G04 动画

1. 只用于新建、选中、拖动、开始、完成、成长。
2. 单次关键动画 150-1000ms。
3. 减少动画开启后取消缩放、飞行和呼吸，仅保留即时状态变化和淡入文字。
4. 动画不得决定业务成功；数据先成功，动画后反馈。

## UI-G05 触控和无障碍

1. 所有关键交互 ≥44×44dp。
2. 不仅依赖颜色表示象限、逾期和推荐。
3. TalkBack 标签包含任务名、象限、截止、进度和操作提示。
4. 轴线、象限背景不抢占任务节点的焦点顺序。

## P7-01 品牌与用户文案清理

```text
P: MUST
USER: 模板图标和工程词让用户觉得 App 是内部工具，不敢信任数据，也不知道下一步。
GOAL: 第一眼像正式产品；任何错误都说清“发生什么、数据是否安全、下一步”。
ENTRY: 启动图标、启动页、首页、任务面板、专注结束、备份恢复、错误状态。
```

FLOW：

```text
启动 → 看到正式品牌标记 → 直接进入象限
错误发生 → 看到人话说明 → 可重试或继续使用
```

RULE：

1. 替换 Android 模板/机器人图标和启动资源；图形为“四象限十字 + 一个行动点”，小尺寸可辨认。

3. 建立集中用户文案模块；日志和内部错误码与用户文案分离。

```text

专注回执 → 这几分钟推进得怎么样？
提醒同步失败 → 任务已经保存，但提醒暂时没有设置成功
```

METRIC：

- 用户可见字符串中禁止词命中数 = 0。
- 启动器图标不是 Android/React Native 模板资源。
- 错误文案 100% 包含可执行下一步或明确“无需操作”。

AC：

- AC-P7-01-01：全文检索禁止词，用户组件和快照中为 0。
- AC-P7-01-02：Android adaptive icon 前景/背景均存在；internal APK 显示正式图标。
- AC-P7-01-03：启动不增加欢迎页或强制引导。

TEST：字符串审计测试；错误状态组件测试；Android resource 检查。

NO：不做复杂品牌动画；不让品牌占用地图空间；不使用远程图片。

## P7-02 任务快速面板两层化

```text
P: MUST
USER: 用户点开任务只是想开始、完成或延期，却先看到完整表单，操作慢且有压力。
GOAL: 点击任务后 250ms 内看到最常用操作；开始、完成、重新安排最多再点一次。
ENTRY: 点击地图节点、清单行、推荐条或精确通知任务。
```

FLOW-A 默认操作层：

```text
任务标题
象限 + 截止
第一小步
[先做 5 分钟]
[完成] [重新安排] [我卡住了]
进度 0 / 25 / 50 / 75 / 100
[编辑更多]
```

FLOW-B 详细层：

```text
标题、象限、重要度、紧急度、截止、下一次开始、第一小步、预计时长、进度、备注、重复、删除
```

RULE：

1. 使用明确状态：`action | details | reschedule | stuck | rescue`，禁止多个冲突布尔值。
2. 默认进入 `action`；主按钮“先做 5 分钟”视觉最强。
3. 进度快捷值点击即保存；保存失败保留原值并提示重试。
4. 进入专注、完成任务前先提交未保存草稿；提交失败不得继续执行危险操作。
5. 详细层本地草稿；关闭有修改时提供“保存 / 放弃 / 继续编辑”。
6. 删除必须显式确认；“暂时不想做”引导到卡住修复而不是直接删除。
7. 标准字体下主按钮始终首屏可见；放大字体使用粘性底栏。

METRIC：

- KPI-G02、G05。
- task_sheet_open 后 `focus_started` 的点击数 ≤1。
- 5 名首次用户中 ≥4 人能在 5 秒内指出“先做 5 分钟”。

AC：

- AC-P7-02-01：点击节点不跳完整详情页。
- AC-P7-02-02：开始、完成、重新安排、卡住入口均在默认层。
- AC-P7-02-03：地图、清单、通知共用同一面板。
- AC-P7-02-04：保存失败不关闭、不清空。

TEST：打开模式；草稿提交顺序；保存失败；字体放大；精确任务入口；重复点击防抖。

NO：不在操作层放十几个字段；不增加新的任务详情页面。

## P7-03 继续上次任务

```text
P: MUST
USER: 用户重新打开 App 后还要重新找任务，行动被打断。
GOAL: 有可继续任务时，一眼继续；无任务时不占空间。
ENTRY: 首页加载完成、App 从后台恢复。
```

RULE：

候选优先级：

```text
1. 正在进行且可恢复的专注会话
2. 最近中断的未完成任务
3. 最近已开始但未完成的任务
4. 无候选则隐藏
```

UI：

```text
继续刚才的任务
修改论文第二章 · 已完成 5 分钟
[继续 15 分钟] [更新进度]
```

1. 紧凑高度；不做半屏大卡。

## P9-04 下一次开始时间与启动提醒

```text
P: MUST
USER: 用户反复改最终截止日期，其实只是需要决定“下一次什么时候再开始”。
GOAL: 分离 nextStartAt 与 deadline；重新安排默认改开始时间，通知直接给第一小步。
```

DATA：

```ts
nextStartAt?: string;
```

RULE：

1. “重新安排”默认修改 `nextStartAt`，明确入口才修改 `deadline`。
2. 快捷项：10 分钟后、今天晚些时候、明天、本周、自定义。
3. 启动提醒显示第一小步，并提供“先做 5 分钟 / 10 分钟后 / 重新安排”。
4. 开始任务后按产品规则清空或重设 `nextStartAt`；完成/删除取消提醒。
5. 移动象限不删除开始时间。
6. 继续使用现有墙钟、时区/DST 和幂等替换能力。
7. 旧任务缺失字段时视为 null；备份新增字段。

METRIC：延期时误改 deadline 的自动化场景 = 0；提醒精确任务率 100%。

TEST：快捷时间、本地时区、DST、完成取消、删除取消、重复调度、旧备份。

NO：不把“10 分钟后”解释为延长最终截止时间。

## P9-05 多次延期温和修复

```text
P: MUST
USER: 多次延期后继续只提供“再延期”，会形成无意义循环。
GOAL: postponeCount ≥2 时提醒缩小、重排、降标准或确认不再需要，不扣已有积分。
```

UI：

```text
这项任务已经重新安排了几次，要不要把下一步再缩小一点？
[缩小到 5 分钟]
[重新安排]
[降低完成标准]
[确认不再需要]
```

RULE：

1. 非阻断提示；用户可关闭。
2. “降低标准”编辑最低交付、第一小步或目标进度。
3. “不再需要”归档/删除、取消提醒、记录原因，不扣分。
4. 主动修复可获得未来的修复奖励，但本阶段不新增复杂分值。
5. 同一 postponeCount 值同一天最多提示一次。

METRIC：提示去重 100%；已有总积分变化 = 0；修复选择可被 OM-05 测量。

TEST：阈值、去重、归档、提醒取消、分数不变、备份。

NO：不清空连续记录；不阻止用户创建其他任务。

# 9. P10：成长反馈与系统级便捷入口

## P10-01 轻量成长物

```text
P: MUST
USER: 成长页只有数字，用户感受不到行动留下了变化。
GOAL: 用一个轻量成长物表现累计进步，不遮挡四象限、不变成游戏系统。
```

建议阶段：种子、发芽、两片叶、小苗、枝条、开花。阈值集中配置：

```ts
interface GrowthStage {
  id: string;
  minScore: number;
  title: string;
  description: string;
}
```

RULE：

1. 使用 RN View、现有动画或本地静态资源；不引入游戏引擎。
2. 首页只显示紧凑状态，如“小苗 240/300”。
3. 成长页显示当前阶段、到下一阶段、最近奖励、成长区贡献和一条洞察。
4. 减少动画时直接切换状态。
5. 阈值单一配置、纯函数计算。

METRIC：阶段计算边界 100%；首页成长区域不超过紧凑头部；完成反馈 ≤1s。

TEST：阈值、升级、降级/撤销、减少动画、深色模式、字体放大。

NO：不实现城市、宠物、商店、金币、装饰或付费。

## P10-02 奖励第一次开始和第一小步

```text
P: MUST
USER: 拖延用户最难的是开始，只奖励最终完成会让早期行动没有反馈。
GOAL: 第一次启动和第一次完成第一小步得到小额、幂等奖励，不可刷分。
```

奖励：

```text
同一任务第一次开始专注 +3
同一任务第一次完成第一小步 +5
任务完成继续使用象限基础分
```

业务键：

```text
task-first-start:{taskId}
task-first-step:{taskId}
task-completion:{taskId}
focus-completion:{focusSessionId}
```

RULE：

1. 任务面板提供可见“第一小步完成”。
2. 点击后记录时间、发一次奖励，可填写下一步；不自动完成任务。
3. 撤销正确回滚记录和奖励。
4. 重挂载、重启、重复点击、备份恢复不得补发或重复发。
5. 2 分钟启动也可获得首次开始奖励，但同一任务只有一次。

METRIC：重复奖励率 = 0；事件可计算 OM-01。

TEST：首次、重复、重启、撤销、恢复备份、重复任务实例独立。

NO：不根据编辑 firstStep 文本自动判定完成。

## P10-03 单条可执行洞察

```text
P: SHOULD
USER: 图表很多但不知道下一步如何调整。
GOAL: 每次只给一条基于本地事实、带操作按钮的建议。
```

首批规则：

```text
A. 本周 ≥4 项成长区任务在 22:00 后首次开始
→ 建议提前设置 nextStartAt

B. 同类任务多次延期且第一小步为空/过大
→ 建议填写 5 分钟第一步

C. 某专注时长样本 ≥5 且完成率明显最高
→ 建议设为默认时长
```

RULE：

1. 本地计算，不上传内容，不使用 AI。
2. 样本不足不输出结论。
3. 每次最多一条；用户关闭后 7 天内不重复。
4. 每条必须有真实操作按钮。
5. 文案描述行为，不评价人格。

METRIC：错误建议率 = 0 自动化规则测试；按钮执行成功率 100%。

TEST：样本阈值、排序、关闭冷却、操作执行、无数据状态。

NO：不建立复杂报表页。

## P10-04 Android 通知动作

```text
P: MUST_ANDROID
USER: 通知只能打开 App，仍需多次寻找任务。
GOAL: 通知直接开始精确任务、延后 10 分钟或打开重新安排。
```

动作优先级：

```text
1. 先做 5 分钟
2. 10 分钟后
3. 重新安排
```

RULE：

1. “先做 5 分钟”冷/热启动均绑定精确任务；重复点击不建第二会话。
2. “10 分钟后”更新 nextStartAt，不改 deadline，幂等替换通知。
3. “重新安排”打开精确任务的 reschedule 面板，不只打开首页。
4. 任务已完成/删除时不开始会话，回首页并说明状态。
5. 如果现有通知库只支持部分动作，按优先级实现并如实报告；不得重写全部基础设施。
6. 权限只在用户设置提醒时申请。

METRIC：KPI-G15；重复 session = 0；误改 deadline = 0。

TEST：冷启动、热启动、进程被杀、重复点击、已完成、已删除、10 分钟后、重新安排。

NO：不为第三个动作更换整套通知框架。

快捷方式：

5. 限制超长/恶意文本；冷/热启动均处理一次，防重复 Intent。
6. 本阶段不做桌面小组件。

METRIC：入口到目标页面 1 次系统动作；重复 Intent 创建数 = 0。

TEST：每个快捷方式、无候选、分享文本、重复 Intent、超长文本。

NO：不自动把分享内容创建成任务。

# 14. 最终产品判断标准

本阶段是否成功，不看新增页面数量，而看用户是否能够：

```text
打开就理解 → 一句话记录 → 一眼知道先做什么 → 一次点击开始
卡住时有出口 → 状态差时压力降低 → 临期时找到最低方案
完成后立即感到成长 → 下次更早开始重要任务
```

任何新增功能若不能缩短上述路径、提高理解或保护数据，都不应进入本阶段。
