# 1. 本轮产品目标

本轮不是继续堆功能，而是解决真实用户使用一段时间后最容易出现的四类问题：

```text
P11：打开后信息太多，不知道唯一下一步；部分用户文案仍像产品术语。
P12：临时想法不方便先记下；任务多后找不到、无法恢复、积压越来越乱。
P13：5 分钟能帮助开始，但论文、报告、考试等长期任务仍缺少持续推进方案。
P14：提醒、备份、无障碍和大数据量必须足够可信，才能长期使用。
```

用户最终应该感受到：

> 打开后只有一个最明显的下一步。  
> 想法 5 秒内可以先记下，不必立刻分类。  
> 任务再多也能找到、恢复和整理。  
> 大任务会被分成连续可执行的步骤和专注时段。  
> 提醒不过度打扰，恢复数据前看得懂且不会误覆盖。

# 3. 全局用户体验规则

## UX-G01 同一时刻只有一个主要行动

首页主行动固定优先级：

```text
ACTIVE_FOCUS
> CONTINUE_RECENT_TASK
> TRIAGE_URGENT_UNSORTED_TASK
> START_RECOMMENDED_TASK
> CAPTURE_FIRST_TASK
> NONE
```

任何状态下，首屏最多一个填充型主按钮。成长、提醒、低状态和推荐原因只能作为辅助信息，不能与主行动争夺注意力。

## UX-G02 产品内部模式对用户隐形

内部可以保留 `actionPointer`、`lowEnergyMode`、`rescueMode`、`growthInsight` 等名称；用户界面只说当前能做什么。

统一用户词：

```text
行动指针       → 现在先做
成长洞察       → 给你的一个建议
成长物         → 直接显示“小苗 / 枝条 / 开花”，不显示分类名
低状态模式     → 今天轻一点
最低可交付版本 → 先做能交的版本
专注复盘       → 这几分钟推进得怎么样？
积分           → 成长值
第一动作       → 第一小步
今日总结/收尾  → 今日回顾
手动紧急度     → 保持我设置的位置
```

## UX-G03 先捕获，再整理

用户突然想到任务时，不得强迫其立即判断象限、截止和预计时长。提供“先记下”，但不把“待判断”做成第五象限。

## UX-G04 大任务只在需要时展开

首页只显示当前第一小步和下一次行动。步骤、推进计划、完成标准只在任务详细层出现，不新增项目管理主导航。

## UX-G05 自动行为必须解释并可撤销

自动推荐、截止联动、生成推进计划、恢复备份、减少提醒都要说明原因。不得静默移动、覆盖或删除用户数据。

## UX-G06 不羞辱、不轰炸

积压、延期、错过计划、低状态都不扣除已有成长值，不使用人格评价，不用威胁性倒计时，不因忽略提醒而增加通知轰炸。

## UX-G07 所有手势都有可见替代

拖动换象限、滑动完成等必须有按钮替代。屏幕阅读器用户无需拖动即可完成全部核心操作。

## UX-G08 数据先成功，动画后反馈

任务写入、Ledger 和提醒协调成功后再播放动画。动画失败不能改变业务结果。

## P11-01 首页唯一主行动协调器

```text
P: MUST
USER: 首页可能同时出现继续任务、推荐、成长、低状态和多个按钮，用户仍会犹豫。
OUTCOME: 打开 App 后 3 秒内能指出唯一下一步。
ENTRY: 冷启动、热启动、专注恢复、任务变更后首页刷新。
```

DATA：建立或扩展纯领域类型：

```ts
type HomePrimaryAction =
  | {type: 'RESUME_ACTIVE_FOCUS'; taskId: string; focusSessionId: string}
  | {type: 'CONTINUE_TASK'; taskId: string}
  | {type: 'TRIAGE_URGENT_UNSORTED'; taskId: string}
  | {type: 'START_RECOMMENDED'; taskId: string; reasons: string[]}
  | {type: 'CAPTURE_FIRST_TASK'}
  | {type: 'NONE'};
```

RULE：

1. 使用第 3 节固定优先级，只返回一个 `HomePrimaryAction`。
2. `RESUME_ACTIVE_FOCUS` 出现时隐藏展开式继续条和展开式推荐条。
3. `CONTINUE_TASK` 出现时推荐降为地图星标，不出现第二个满宽按钮。
4. 无任务时主行动为“记下第一项任务”，点击直接聚焦输入框。
5. 成长树仅为紧凑状态，不可使用填充型主按钮。
6. “今天轻一点”只改变推荐和默认时长，不成为第二个主卡片。
7. 360×800dp 标准字体下：首页顶部信息区不超过可用高度 25%，四象限地图首屏可见。
8. 字体放大时允许垂直滚动，但主行动先于统计和成长信息。

METRIC：M-01、M-02。

AC：

- 任意测试状态中最多一个 primary CTA。
- 活动专注一次点击恢复，不创建新会话。
- 无可继续任务时不显示空的继续卡片。
- 推荐任务仍在地图中高亮，但不与继续操作争抢。

TEST：为六种 `HomePrimaryAction` 状态建立纯函数测试和首页组件测试；验证重挂载稳定、不随机变化。

NO：不新增首页轮播、多个横向卡片或新的导航页。

# 6. P12：快速捕获、查找、恢复与积压整理

## P12-01 “待判断”快速收集箱

```text
P: MUST
USER: 临时想到一件事时只想立刻记下，不想先判断象限，强制分类会导致放弃记录或乱放。
OUTCOME: 只输入标题即可在 5 秒内保存，稍后两问完成分类。
ENTRY: 全局 +、应用快捷方式、分享创建、快速输入解析置信度低。
```

DATA：优先扩展现有 Task；建议兼容字段：

```ts
type TaskPlacementState = 'QUADRANT' | 'UNSORTED';
placementState?: TaskPlacementState; // 缺失视为 QUADRANT
```

RULE：

1. 地图空白处创建始终属于该象限，不进入待判断。
2. 全局快速添加增加次操作“先记下”；只要求非空标题。
3. `UNSORTED` 不显示在四象限地图中，不作为第五象限。
4. 首页仅在数量 >0 时显示紧凑入口：`待判断 · N`。
5. 一次整理最多 3 项，一项只问：

```text
这件事对你有长期影响吗？ [有] [没有]
它需要很快处理吗？       [需要] [不急]
```

6. 根据答案写入连续重要度/紧急度和 legacy Q1-Q4；用户可在确认前修改。
7. 有明确截止且 24 小时内到期的待判断任务，首页主行动可变为“先判断这项即将到期的任务”。
8. 待判断任务不参与普通推荐和象限完成奖励。
9. 待判断任务允许编辑和删除；开始专注前先要求快速归类，最多两问，不进入完整表单。
10. 完成待判断任务前必须归类，确保奖励原因一致；不得使用临时象限静默发分。
11. 旧任务和旧备份缺失字段时默认为 `QUADRANT`。

METRIC：M-03、M-04；待判断任务 24 小时归类率只建立基线，不设置虚假增长目标。

AC：

- 只输入标题可保存。
- 待判断不污染地图和四象限数量。
- 两问后任务立即出现在正确象限。
- 归类失败保留原任务和答案草稿。

TEST：旧数据迁移；分享/快捷入口；低置信度；紧急待判断主行动；归类边界；开始前归类；备份恢复。

NO：不新增第五象限；不默认把所有未判断任务塞进成长区；不因未分类而丢失任务。

## P12-02 本地全局搜索

```text
P: MUST
USER: 使用一段时间后任务很多，用户找不到某项任务，只能滚动四个区。
OUTCOME: 输入标题、第一小步或备注即可找到，并直接开始、编辑、完成或恢复。
ENTRY: 首页顶部搜索按钮；四区清单搜索入口。
```

RULE：

1. 搜索范围：标题、第一小步、备注；包含未完成、待判断、已完成、归档。
2. 默认本地搜索，不联网，不做拼音库，不增加大型索引依赖。
3. 规范化：trim、多空格合并、大小写不敏感；中文按原字符包含匹配。
4. 150ms 内防抖；结果最多先展示 50 条，继续滚动分页。
5. 结果按：未完成匹配度、最近更新、待判断、已完成排序；必须显示状态和象限。
6. 每条结果可见操作：

```text
未完成：开始 / 编辑 / 完成
待判断：判断 / 编辑
已完成：查看 / 恢复
归档：恢复到待判断
```

7. 点击结果后精确定位；不只打开首页。
8. 搜索为空时显示最近访问任务，最多 5 项；无结果时提供“记下这个任务”，但不自动创建。
9. 最大字体和屏幕阅读器可用。

METRIC：M-05、M-06。

AC：5000 条任务基准 p95 ≤100ms；搜索不引起地图全量重排；无结果不崩溃。

TEST：中文、英文大小写、空格、备注、完成任务、5000 条性能、直接操作、无障碍标签。

NO：不接网络搜索；不在每次输入时写存储；不建立第二套任务索引数据库，除非基准证明必要。

## P12-03 已完成记录与安全恢复

```text
P: MUST
USER: 用户误点完成或想回看成果时，5 秒撤销过后没有清楚入口，也担心任务消失。
OUTCOME: 能找到已完成任务并恢复，且不会重复获得完成奖励。
ENTRY: 搜索结果、成长页“最近完成”、我的 → 已完成任务。
```

RULE：

1. 分组：今天、最近 7 天、更早；使用虚拟列表。
2. 显示：标题、完成时间、所属象限、实际专注时间、获得成长值原因。
3. 恢复后回到未完成状态；不自动恢复已经过期的提醒。
4. 5 秒即时撤销继续使用现有 operation ledger 并回滚奖励。
5. 从历史页晚恢复时：保留原奖励记录为已消费业务键；该任务再次完成不得重复获得同一 `task-completion:{taskId}` 奖励。
6. 恢复后提示：

```text
任务已恢复。之前的完成成长值不会重复发放。
[安排下一次开始]
```

7. 重复任务实例只恢复当前实例，不影响后续实例。
8. 恢复失败不改变原完成状态。

METRIC：M-07。

AC：恢复后地图/清单同步；重启后仍未完成；重复完成不重复发分。

TEST：即时撤销、历史恢复、重复完成、重复任务、过期提醒、失败回滚、旧备份。

NO：不通过复制任务代替恢复；不静默扣除已累计成长值；不删除完成历史。

OUTCOME: 每次只处理少量旧任务，减少噪声，不责备、不扣分。

archivedAt?: string;

# 7. P13：长期任务的分步推进与按时完成

## P13-01 “做到什么算完成”

```text
P: MUST
USER: “写论文、准备考试、做项目”边界模糊，用户开始了也不知道何时算完成。
OUTCOME: 大任务可以写一个清楚、可验证的完成标准，但普通小任务不被强迫填写。
ENTRY: 预计时长 >60 分钟、延期 ≥2 次、救援计划、用户主动“编辑更多”。
```

DATA：

```ts
completionDefinition?: string; // 建议最大 300 字
```

RULE：

1. 字段用户名：`做到这里就算完成`。
2. 不强制；小任务默认折叠。
3. 任务面板只在已填写时显示一行摘要。
4. 救援模式的最低版本可以建议写入或关联该字段，但不得覆盖用户已有标准。
5. 内容只保存在本机并进入备份。

AC：旧任务无字段可正常加载；保存失败保留草稿；完成时可查看标准但不强制二次确认。

TEST：Schema 迁移、备份、最大长度、救援兼容、空值。

NO：不要求每个任务填写；不把它做成新的必填创建页。

## P13-02 最小行动步骤

```text
P: MUST
USER: 第一小步解决首次启动，但长期任务完成第一步后又失去方向。
OUTCOME: 一个长期任务可以有 1-12 个有序步骤，首页永远只显示当前一步。
ENTRY: 任务详细层“添加推进步骤”；大任务温和建议。
```

DATA：优先复用现有子任务结构；若没有，建议：

```ts
type TaskStepStatus = 'PENDING' | 'ACTIVE' | 'DONE' | 'SKIPPED';

interface TaskStep {
  id: string;
  title: string;
  order: number;
  estimatedMinutes?: number;
  status: TaskStepStatus;
  createdAt: string;
  completedAt?: string;
}

progressSource?: 'MANUAL' | 'STEPS';
steps?: TaskStep[];
```

RULE：

1. 最多 12 步，标题非空；默认只有一项 `ACTIVE`。
2. 创建步骤计划时，明确询问是否让进度按步骤计算；默认选择 `STEPS`，用户可保留手动进度。
3. `STEPS` 模式进度按预计分钟加权；缺失时按步骤数平均。
4. 当前 `ACTIVE` 步骤投影为现有 `firstStep`，所有旧 UI 和通知继续读统一 selector；禁止两套可独立编辑的真源。
5. 完成当前步骤后，下一项 `PENDING` 自动变 `ACTIVE`，首页和通知立即更新。
6. 完成步骤不发象限完成奖励；只保留现有“第一次完成第一小步”一次性奖励，防止刷分。
7. 已经产生专注历史的步骤删除时改为 `SKIPPED`，不硬删历史。
8. 支持可见上移/下移按钮，拖动排序只是增强。
9. 复制任务和重复任务实例复制步骤模板，但生成新 stepId、重置状态和奖励键。

METRIC：步骤完成后下一步可见 ≤300ms；重复步骤奖励 = 0。

AC：完成一步不完成整项任务；最后一步完成后只提示“是否完成整项任务”，不自动完成。

TEST：迁移、排序、进度、投影、跳过、复制、重复任务、Ledger 幂等、备份恢复。

NO：不新增项目管理树、依赖图、甘特图；不为每一步发完整任务分。

## P13-03 分段推进计划

```text
P: MUST
USER: 预计 3 小时的任务即使开始过 5 分钟，仍可能在截止前没有足够时间完成。
OUTCOME: 用户可在 60 秒内把剩余工作分成 15/25/45 分钟的若干次行动，首页只突出最近一次。
ENTRY: 预计剩余 >60 分钟、延期 ≥2、截止 7 天内但无 nextStartAt、用户主动“安排推进计划”。
```

DATA：不要创建子任务；建立附属于原任务的计划：

```ts
type PlannedWorkStatus = 'PLANNED' | 'STARTED' | 'DONE' | 'SKIPPED';

interface PlannedWorkSession {
  id: string;
  taskId: string;
  stepId?: string;
  plannedStartAt: string;
  plannedMinutes: 15 | 25 | 45;
  status: PlannedWorkStatus;
  focusSessionId?: string;
  createdAt: string;
  completedAt?: string;
}
```

FLOW：

```text
这项任务还需要大约 180 分钟。
每次做多久？ [15] [25] [45]
希望在哪些时间推进？ [今天] [明天] [选择日期]
预览计划 → 保存
```

RULE：

1. 一次最多生成 10 个未来行动；至少 1 个。
2. 使用可注入时钟和本地时区；不得用 UTC 字符串截断。
3. 剩余分钟优先取未完成步骤预计分钟总和；否则取任务预计时长 × 剩余进度。
4. 保存前展示日期、时长、对应步骤；用户可删除或调整单次行动。
5. 只为最近一次未来行动设置启动提醒；完成/跳过后再协调下一次，避免通知轰炸。
6. 首页唯一主行动可显示：

```text
今晚 20:30 · 修改论文第二章
现在先做：列出三个小标题
[开始 25 分钟]
```

7. 点击后复用现有 Focus Runtime，精确绑定 taskId、可选 stepId 和计划 sessionId。
8. 同一 planned session 重复点击不得创建多个 focus session。
9. 错过计划不判失败；下次打开提供：`现在开始 / 重新安排剩余计划 / 跳过这次`。
10. 可一键将所有未开始行动顺延一天，但不能越过最终截止而不提示。
11. 完成任务后取消剩余计划和提醒；恢复任务时不自动恢复旧计划，先让用户确认。

METRIC：M-09、M-10、M-11。

AC：计划保存后 nextStartAt 与最近行动一致；首页只显示最近一次；重启后计划完整。

TEST：计划生成、跨月/跨年/DST、重复点击、只调度最近一次、错过、顺延、完成取消、恢复任务、备份。

NO：不创建多个任务卡；不一次注册 10 条平台通知；不自动替用户安排未经确认的日期。

## P13-04 可解释的时间不足判断

```text
P: MUST
USER: 用户以为还有时间，但剩余工作量已经无法由现有计划覆盖，最后仍进入救火。
OUTCOME: 系统在任务面板中温和说明“按现在安排可能来不及”，并给出三个可执行出口。
ENTRY: 打开任务、保存推进计划、App 恢复时重新计算。
```

建立纯函数：

```ts
type DeliveryRisk = 'UNKNOWN' | 'OK' | 'NEEDS_PLAN' | 'AT_RISK';

deriveDeliveryRisk({
  remainingMinutes,
  plannedMinutesBeforeDue,
  dueAt,
  nextStartAt,
  now,
}): DeliveryRisk;
```

建议规则：

```text
UNKNOWN：无截止或无剩余估计。
OK：截止前已计划分钟 >= 剩余分钟。
NEEDS_PLAN：截止 7 天内，剩余 >60 分钟，且没有未来计划。
AT_RISK：截止前已计划分钟 < 剩余分钟，或 24 小时内剩余明显大于计划。
```

用户文案：

```text
按现在的安排，时间可能不够。
[增加一次行动] [先做能交的版本] [调整截止时间]
```

RULE：

1. 不显示黑盒风险分数或人格评价。
2. 不在首页所有节点上铺红色警报；只在任务面板和行动建议原因中出现。
3. `AT_RISK` 可调用现有救援流程；不得另建救援系统。
4. 用户关闭后同一任务 24 小时内不重复提示，除非截止进入更近区间。

AC：规则纯函数、结果稳定、边界可测试。

TEST：无数据、计划充足、无计划、大于/等于边界、24 小时、关闭频率、救援衔接。

NO：不声称“你一定会延期”；不自动改截止或删除范围。

## P13-05 专注结束后的连续推进

```text
P: MUST
USER: 完成一次 5 分钟后，用户容易停在复盘页，不知道下一步或下次何时继续。
OUTCOME: 专注结束后最多一次选择即可继续、完成当前步骤或安排下一次。
ENTRY: Focus session 正常完成或提前结束。
```

```text
这几分钟推进得怎么样？
[完成了这一步]
[继续 15 分钟]
[安排下一次]
[这一步还没做完]
```

RULE：

1. 若绑定 planned session，结束后更新该 session 状态和实际 focusSessionId。
2. “完成了这一步”推进到下一 ACTIVE 步骤，不自动完成整项任务。
3. “继续 15 分钟”复用当前任务和步骤，不创建重复结算。
4. “安排下一次”打开轻量时间选择，默认建议下一个可用计划时间。
5. 关闭面板时保留专注记录，不强制填写备注。
6. 首页主行动立即更新为下一步或下一计划。

AC：从专注结束到下一行动最多 1 次点击；重挂载不重复记录步骤或奖励。

TEST：计划绑定、步骤推进、继续、安排、关闭、重复提交、任务已完成冲突。

# 8. P14：提醒克制、数据恢复、无障碍与长期可靠性

## P14-01 提醒预算与重复延后修复

```text
P: MUST
USER: 提醒太多会被关闭；提醒太少或重复创建会失去信任。
OUTCOME: 用户明确安排的提醒可靠，系统主动提醒克制，多次延后后改为帮助缩小任务。
ENTRY: 所有主动提醒调度、nextStartAt、推进计划、通知“10 分钟后”。
```

DATA：复用提醒偏好，必要时增加：

```ts
interface ReminderBudgetPreference {
  maxSystemRemindersPerDay: number; // 默认 6
  maxSystemRemindersPerTaskPerDay: number; // 默认 2
  lowEnergyMaxPerDay: number; // 默认 3
}
```

RULE：

1. 用户显式设置的 `nextStartAt` 不得被系统预算静默丢弃；若超过预算，保存时说明并让用户选择。
2. 系统自动建议/进度提醒受预算限制：普通全局 ≤6/日、单任务 ≤2/日；“今天轻一点”全局 ≤3/日、单任务 ≤1/日。
3. 同一任务同一时刻最多一条待触发启动提醒，使用幂等替换。
4. 通知“10 分钟后”只改 nextStartAt，不改 dueAt。
5. 同一任务连续延后 3 次后，不增加通知数量；下次打开任务显示“要不要把第一小步再缩小一点？”并复用卡住修复。
6. 推进计划只调度最近一次未来行动。
7. 手机重启、时区变化和 DST 后重新协调，不能重复。
8. UI 未获得精确闹钟能力时不得承诺“准时”，使用“约 {time} 提醒”。

METRIC：M-12；重复通知/重复会话 = 0。

TEST：预算边界、显式提醒、低状态、连续延后、重启、DST、重复点击、任务完成取消。

NO：不因用户忽略提醒而升级轰炸；不静默删除用户明确安排。

## P14-02A 备份预览与安全替换

```text
P: MUST
USER: 用户导入备份前不知道里面有什么，也担心覆盖当前任务。
OUTCOME: 任何写入前先看到内容摘要；替换前自动保存当前快照；失败可回滚。
ENTRY: 我的 → 数据与备份 → 选择备份文件。
```

RULE：

1. 选择文件后先只读解析和严格校验。文件级关键结构无效时直接停止且不写入；只有现有校验器能够安全隔离单条坏记录时，才允许隔离并报告。显示：

```text
备份日期
应用/Schema 版本
任务总数、未完成、已完成、待判断
专注记录数
成长记录数
是否存在警告或损坏记录
```

2. 预览期间写入次数必须为 0。
3. 提供：`用备份替换当前数据 / 取消`；替换前再次显示当前数据将受影响。
4. 替换前自动创建当前本机安全快照，写入成功后保留最近一份。
5. 使用现有 restore journal / 事务；任何步骤失败恢复原数据。
6. 恢复后重新计算 selector、计划、nextStartAt 和平台通知；不得导入旧平台通知 ID。
7. operation ledger 和奖励业务键保持，不能因恢复重复发放历史成长值。
8. 结果摘要：恢复多少任务、是否存在被安全隔离的坏记录（仅在校验器支持时）、提醒是否重新设置；否则明确说明整次恢复未执行。

METRIC：M-13、M-14。

TEST：预览零写入、有效替换、损坏文件、事务中断、自动快照回滚、Ledger 去重、通知重协调。

NO：不直接覆盖；不只显示文件名；不在失败后留下半份数据。

## P14-02B 备份合并

```text
P: SHOULD
USER: 用户在新设备已经创建了任务后，仍希望合并旧备份，而不是二选一覆盖。
OUTCOME: 在模型能安全去重时提供合并；无法保证时明确不实现，不以猜测覆盖数据。
```

合并规则：

1. 任务同 ID：`updatedAt` 较新者为主。时间相同但内容冲突时，只有存在能够完整重映射任务、步骤、计划、专注、提醒和 Ledger 引用的服务，才允许把备份副本改为新 ID；否则将该条列为冲突并停止合并，不得猜测覆盖。
2. immutable 记录按 id / operationKey 并集去重。
3. 重复任务实例按 recurrence business key 去重。
4. 偏好默认保留当前设备；用户可单独选择恢复偏好。
5. 通知全部重新计算，不合并平台 ID。
6. 合并前仍自动快照，失败回滚。

## P14-03 无障碍等价操作与自适应视图

7. 颜色不是唯一状态表达。
