# Start Five 当前产品问题与研究缺口审计

更新时间：2026-08-22（Asia/Shanghai）

审计基线：`main`；R20-01 已关闭，R20-02 设备矩阵准备完成但无 online 设备

产品阶段判断：`INTERNAL_BETA / NOT_RELEASE_READY`

## 1. 审计结论

Start Five 已经不是静态原型。P0–P19 的四象限任务闭环、专注、成长、提醒、备份、恢复和共享交互可靠性均有真实源码与自动测试；R20-01 authoritative accepted inventory 已连续两次达到 77/77 suites、839/839 tests PASS。

当前主要矛盾不是继续增加功能，而是以下三种失衡：

1. 功能丰富度已经超过默认交互的收敛程度。
2. 自动合同证据很强，真实设备、真实用户和长期运行证据明显不足。
3. 数据与业务规则较完整，错误诊断、运行观测、用户反馈和发布治理仍然薄弱。

因此当前只能定义为功能较完整的内部 Beta。Android 完整设备矩阵、iOS 构建与真机、首次用户测试、生产诊断和发布工程完成前，不得写成 `RELEASE_READY`。

## 2. 证据分级

本文严格区分三类结论：

| 标记 | 含义 | 可否直接作为缺陷结论 |
| --- | --- | --- |
| `CONFIRMED_SOURCE` | 当前源码或配置可以直接证明 | 可以 |
| `HIGH_RISK_PENDING_DEVICE` | 源码已有实现，但真实设备行为尚无完整证据 | 不能写成已通过，也不能写成必现缺陷 |
| `RESEARCH_HYPOTHESIS` | 产品/心理/认知风险，需要目标用户观察验证 | 不能替代用户研究 |

历史截图中“任务标题重复”在当前 `TaskEditor` 源码中已移除；旧进度并发根因已有数据层修复与合同测试。两项均不再列为当前必现缺陷，但进度失败诊断和真机拖动仍在本审计中保留。

## 4. 用户体验与信息架构

### 4.1 核心承诺被功能宽度稀释

`RESEARCH_HYPOTHESIS`

产品最清晰的承诺是“先开始五分钟”，但默认产品已经同时承载四象限、进度、步骤、计划、重复任务、专注日程、成长、低能量救援、提醒、备份和大量设置。对于拖延、低能量或焦虑用户，系统整理可能替代真正开始。

验证问题：首次用户能否在不阅读说明的情况下，直接完成“创建任务 → 放入象限 → 先做五分钟”，还是先进入设置、进度或整理流程。

### 4.2 四象限语义需要真实学习证据

`RESEARCH_HYPOTHESIS`

“救火区 / 成长区 / 干扰区 / 清理区”具有品牌辨识度，但比传统“重要/紧急”重新增加一层语言学习。需要验证用户是否能区分“干扰区”和“清理区”，以及用户把象限理解为任务性质、当下优先级还是情绪状态。

### 4.3 任务操作层决策密度过高

`CONFIRMED_SOURCE`

任务 Sheet 同时提供第一步、完成定义、进度、完成、重新安排、帮助、更多、编辑、专注时段和开始五分钟等操作。能力齐全，但主动作与次动作竞争，可能削弱“立刻开始”。

建议验证并收敛为：一个主动作“先做五分钟”；两个常用次动作“完成 / 修改进度”；移动、复制、删除、重复等进入更多操作。

### 4.4 进度模型过粗

`CONFIRMED_SOURCE`

当前快捷进度只有 0%、25%、50%、75%，100% 由“完成任务”承担。对长任务而言步进偏粗，用户也可能疑惑为什么没有 100%。可以保留四档快捷值，但需强化“完成即 100%”语义，或提供步骤数/自定义进度。

### 4.5 视觉密度与层级仍需设备证据

`HIGH_RISK_PENDING_DEVICE`

大卡片、大按钮和近全屏 Sheet 提高触控面积，但一个屏幕可见任务较少；Sheet、底部导航、奖励条、Snackbar 和页面错误可能同时竞争注意力。P19 已明确保留 320dp + 最大字体，以及 Sheet 回弹/奖励/Snackbar 节奏两个 P2 风险。

## 5. 交互、错误与恢复

### 5.1 长按拖动仍不能仅靠合同测试关闭

`HIGH_RISK_PENDING_DEVICE`

当前源码已实现 1000ms 持续选中、同手势或第二次触碰拖动、跨象限提交失败回滚和无障碍替代移动。但以下仍需真实触摸验证：

- 长按与父页面滚动竞争。
- 1000ms 是否让用户误以为不可拖动。
- 象限边缘、低帧率、大字体下的目标命中。
- TalkBack 开启后的选择和移动。
- 前后台切换时布局模式是否可靠退出。

### 5.2 错误状态需要按业务域隔离

`CONFIRMED_SOURCE`

多个任务操作共享根页面 `actionError`，错误又会传入不同 Sheet。即使旧进度并发问题已修复，仍存在旧错误串入新上下文、同一页面出现多条通用红色错误的协调风险。

建议建立包含 `operationId / taskId / code / retryable / userMessage` 的统一错误对象，并由每个 Sheet/操作实例拥有自己的错误生命周期。

### 5.3 设置持久化需要真正的失败闭环

`CONFIRMED_SOURCE`

设置修改应采用以下任一契约：

1. 等待持久化成功后更新 UI；或
2. 乐观更新，失败后回滚，并显示可重试错误。

当前“界面更新 + 写入失败静默忽略”不能作为正式产品行为。

### 5.4 启动与数据异常缺少用户可见恢复入口

`CONFIRMED_SOURCE`

需要用加载态替代空白 Fragment，并为超时、迁移失败、存储读取失败提供：重试、只读启动、导出诊断或安全恢复入口。不能让用户把数据初始化问题理解为 APP 卡死。

## 6. 数据、备份、隐私与安全

### 6.1 本地优先的边界

本地优先减少账户、服务器和网络攻击面，是当前明确优势；代价是换机、丢机和多设备使用依赖手工备份。当前不支持安全合并是正确的 fail-closed 选择，但恢复替换边界必须始终显式告知用户。

### 6.2 备份摘要不等于加密或认证

`CONFIRMED_SOURCE`

当前备份使用规范 JSON、Base64 和 SHA-256 摘要，可检测偶然损坏，但不能隐藏内容；摘要不带密钥，修改者也可重新计算，不能提供来源真实性。正式版应至少明确标记“导出文件未加密”，后续考虑密码派生密钥与带认证加密。

### 6.3 8 MiB 容量门需要提前治理

`CONFIRMED_SOURCE`

产品具有任务、步骤、计划、专注、成长、提醒和 ledger 历史，又面向 5000 条任务规模；Android/iOS 文件桥的 8 MiB 限制可能在长期使用后变成突然失败。需要增加导出前容量估算、接近上限预警、历史归档或压缩策略。

### 6.4 本地标识符不适合未来跨设备合并

`CONFIRMED_SOURCE / FUTURE_SCOPE`

部分标识符基于时间、序列和随机数，当前单设备本地使用碰撞风险较低；如果未来开放跨设备同步或合并，应升级为明确的全局唯一标识和完整引用重映射。P14-02B 在服务完整前继续保持阻断。

## 7. 性能与工程可维护性

### 7.1 根页面是当前最大协调风险

`CONFIRMED_SOURCE`

`QuadrantHomeScreen` 同时组合四个主页面、任务编辑、布局提交、专注、成长、设置、通知、备份和多个顶层 overlay。高 state/effect 数量与少量 memo 化意味着状态推理和渲染优化都较困难。

拆分目标不应只是减少行数，而应建立清晰边界：

- 每个主页面独立 ViewModel。
- Sheet/Overlay 使用显式状态机。
- 持久化、导航和错误副作用从展示组件移出。
- 派生列表和统计使用稳定 selector，并用设备性能数据决定 memo 化。

### 7.2 数据层可靠但维护表面很大

`CONFIRMED_SOURCE`

任务仓库、核心服务和备份服务均为大型模块，包含分页、摘要、日志、迁移、journal 与回滚。现有合同测试是优势，但还需要真实长期数据样本、跨版本迁移演练和故障注入，防止“测试夹具正确、用户多年数据失败”。

### 7.3 5000 条逻辑测试不等于 5000 条真机流畅

`HIGH_RISK_PENDING_DEVICE`

尚缺低端 Android 的首屏时间、拖动帧率、长列表内存、Sheet 打开耗时、后台恢复和通知重建性能记录。React Test Renderer 与内存仓库不能代替 JS/UI 线程的设备证据。

## 8. 无障碍与跨平台

源码已有无障碍标签、角色、live region、列表回退和非拖动移动入口，这是有效基础；以下仍是外部证据缺口：

- TalkBack 的真实焦点顺序、拖动替代操作和 Sheet 返回。
- VoiceOver、动态字体、安全区和键盘。
- 320dp 与 fontScale 2.0 的完整页面。
- Reduce Motion 是否覆盖所有回弹、奖励和自动消失提示。
- 四象限是否同时使用文字/结构，而不是只依赖颜色。

Android 结果不能替代 iOS 证据，自动语义树也不能替代读屏用户操作。

## 9. 产品研究与观测闭环

### 9.1 指标定义已完成，真实采集未接通

`CONFIRMED_SOURCE`

项目已定义开始、提醒、救援、成长等产品事件，但默认装配为 No-op，当前只能证明“指标机制被设计和测试”，不能证明“真实用户开始率已提升”。

下一步应先决定隐私边界，再接入本地持久化研究端口；任何外发分析都必须另行取得用户同意并更新隐私说明。

### 9.2 首次用户证据仍为空

`HIGH_RISK_PENDING_EXTERNAL_USERS`

至少 5 名未读说明的目标用户需要无指导完成：

`创建任务 → 判断象限 → 移动任务 → 先做五分钟 → 修改进度 → 完成任务 → 找到备份 → 从一次失败中恢复`

记录实际卡住、误点、寻找路径和原话；开发者解释后完成不能计为首次可用性通过。

### 9.3 成长和救援语气需要心理安全验证

`RESEARCH_HYPOTHESIS`

成长值、卡住、救援、低能量和延后治理可能提供支持，也可能让焦虑用户感到被评价或被家长式提醒。需要观察用户失败后是否愿意再次打开 APP，而不是只记录按钮点击。

## 10. 测试、发布与运营

### 10.1 839 项 PASS 的正确解释

839 项 accepted tests 证明当前业务契约、迁移和大量故障路径具有强回归基础；它不证明系统长按、原生键盘、通知权限、文件选择器、系统杀进程、TalkBack/VoiceOver、触控帧率和低端机内存已经通过。

当前缺少覆盖完整真实流程的 Detox/Maestro/Appium 类设备端到端体系；R20-02 runner 只生成明确标注为 `AUTO_CAPTURE_NOT_MANUAL_ACCEPTANCE` 的采集证据。

### 10.2 版本与发布治理不统一

`CONFIRMED_SOURCE`

`package.json`、Android、iOS 和关于页面的版本来源并未统一；关于页面仍存在硬编码。正式发布前应由构建配置单一注入版本、commit 和渠道信息。

### 10.3 缺少生产支持基础设施

`CONFIRMED_SOURCE / RELEASE_GAP`

尚无完整证据证明已具备受管 release keystore、AAB/IPA 流水线、崩溃诊断、回滚方案、正式反馈渠道和商店隐私合规。完成前保持 internal 包定位。

## 11. 建议执行顺序

### P0：先关闭可靠性与证据缺口

1. 修复设置写入静默失败，统一失败回滚和重试。
2. 建立错误代码、操作上下文和隐私安全的本地诊断日志。
3. 增加启动加载、超时与恢复界面。
4. 有设备后执行 R20-02，不用自动测试替代手工拖动、TalkBack、通知和重启。
5. 在 macOS/Xcode 完成 iOS 构建和基础真机验收。
6. 配置真实反馈入口。

### P1：收敛默认用户路径

1. 降低任务 Sheet 的主动作竞争。
2. 明确进度与完成的关系。
3. 依据设备数据拆分根页面并优化渲染。
4. 增加备份容量预警与未加密提示，设计认证加密升级。
5. 接入隐私友好的本地产品指标端口。

### P2：建立真实产品结论

1. 完成至少 5 名首次用户观察。
2. 只依据高频证据修复 320dp、最大字体、动效和可发现性。
3. 验证成长/救援语气的心理安全性。
4. 统一版本、签名、发布、诊断和回滚治理。

## 12. 当前边界

- 本审计没有重新实施 P0–P19，也没有改变业务 schema。
- 本审计不把历史截图中的已修问题重新标记为当前必现。
- 本审计不把源码实现、自动测试或自动截图写成 DEVICE PASS。
- 本审计不建议在 R20-02/R20-04 证据前继续增加 AI、社区、账号或新后端。
- 最新阶段状态仍以 `docs/CURRENT_RESEARCH_ROUTE.md` 为入口，设备执行状态以 `docs/R20_02_ANDROID_DEVICE_MATRIX_PROGRESS.md` 为准。
